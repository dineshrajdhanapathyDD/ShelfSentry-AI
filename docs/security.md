# Security boundaries (ShelfSentry AI)

_Requirement 26.3 — the security boundary, as actually implemented. Each
boundary below points at the real module that enforces it and the test that
asserts it, so the claim is checkable, not aspirational._

The guiding principle: giving the agent *vision tools* must never become giving
the agent *the machine*. The agent touches perception only through a restricted
MCP surface, addresses media only by opaque server-minted handles, and the AWS
mode fails loud rather than silently substituting local behavior.

## 1. MCP tool capability boundary

**Enforced by:** `backend/shelfsentry/mcp/server.py`
**Asserted by:** `backend/tests/mcp/test_security_boundary.py`,
`backend/tests/mcp/test_arg_validation.py`

The MCP server exposes exactly four tools — `analyze_shelf_image`,
`inspect_region_crop`, `compare_shelf_frames`, `get_annotated_evidence`. Each
takes only an `inspection_id` plus typed ids/boxes:

- **No filesystem path, no arbitrary URL, no shell, no credential args.** The
  typed `*Args` models (`AnalyzeShelfImageArgs`, `InspectRegionCropArgs`,
  `CompareShelfFramesArgs`, `GetAnnotatedEvidenceArgs`) carry no field that names
  a path, URL, credential, or shell command, so the derived JSON schema cannot
  expose one. The server resolves the actual bytes through an injected
  `MediaResolver` whose Protocol is deliberately tiny and transport/credential
  free.

- **Schemas are strict (`additionalProperties: false`).** Every `*Args` model
  sets `model_config = ConfigDict(extra="forbid", ...)`, so any unexpected
  argument is rejected at the boundary.

- **Validation before execution.** `validate_tool_args(tool_name, raw_args)` is
  the single entry point every invocation passes through *before* any media is
  resolved or any vision function runs. On failure it raises a structured
  `McpToolError` (stable `code`, offending `tool` and `field`) with no resolver
  or vision side effect.

## 2. Storage media-reference boundary

**Enforced by:** `backend/shelfsentry/data/storage.py` (local) and
`backend/shelfsentry/data/aws_storage.py` (AWS)
**Asserted by:** `backend/tests/data/test_storage.py`,
`backend/tests/data/test_aws_storage.py`

Media is addressed only by **opaque, server-minted handles** of the form
`media://<hex-token>`; the hex token is generated by the adapter and never
accepted from the agent.

- **Crafted / foreign refs are rejected before any I/O.** On every read the
  token is re-validated to be pure lowercase hex of the expected length, and the
  resolved location is confirmed to live inside the scoped area. A crafted
  reference (`../`, an absolute path, an `s3://` URL, a drive letter, a NUL byte,
  a foreign bucket) is rejected with `InvalidMediaRef` *before* any file is
  opened or any S3 call is made (`_media_path_for_token` / `_parse_ref` locally;
  `_key_for_token` / `_parse_ref` in AWS).

- **Local base-dir scoping.** `LocalStorageAdapter` confirms the resolved media
  path's parent is exactly the configured media directory (defense in depth on
  top of the token regex). Record ids used as filenames (`inspection_id`,
  `job_id`) are sanitized by `_sanitize_record_id` (rejecting separators, `..`,
  drive letters, NUL).

- **AWS bucket/prefix scoping.** `AwsStorageAdapter` composes keys only under
  `<key_prefix>media/` and re-asserts that containment with no traversal on every
  read, so a crafted ref cannot point outside the configured bucket/prefix.

## 3. Fail-loud mode switch (no silent local substitution, no secrets)

**Enforced by:** `backend/shelfsentry/config/mode.py`
**Asserted by:** `backend/tests/config/test_mode.py`

- **AWS mode never silently substitutes local.** `resolve_runtime_config(...)`
  resolves the `SHELFSENTRY_MODE` switch once at startup. When AWS mode is
  selected and any required key (`SHELFSENTRY_S3_BUCKET`,
  `SHELFSENTRY_DDB_TABLE`, `SHELFSENTRY_AWS_REGION`) is missing, it raises
  `ModeConfigurationError` naming **every** missing key. There is no branch that
  falls back to a local/mock runtime for an incompletely-configured AWS
  selection (Req 16.4, 17.3).

- **No secrets in config.** Only non-secret resource *names* (bucket, table,
  region) are read from the environment. AWS credentials are resolved later by
  the standard boto3 provider chain at call time — nothing in the config layer,
  the storage adapter, or the Bedrock model reads, stores, or logs a credential
  (`config/mode.py`, `data/aws_storage.py` "No embedded secrets",
  `agent/bedrock.py`).

## 4. CloudFormation security posture

**Enforced by:** `infrastructure/template.yaml`
**Asserted by:** `backend/tests/infrastructure/test_template.py`

The single CloudFormation template (no CDK, no Terraform) provisions AWS mode
with a hardened posture:

- **Private, encrypted, public-access-blocked S3.** The media bucket sets
  `BucketEncryption` (AES256 + bucket keys), `PublicAccessBlockConfiguration`
  with all four blocks `true`, `BucketOwnerEnforced` ownership, versioning, and a
  lifecycle expiry. A bucket policy additionally denies any non-TLS
  (`aws:SecureTransport=false`) access.

- **Least-privilege IAM.** Each Lambda has its own role scoped to its own log
  group, the media bucket under the upload prefix only
  (`${MediaBucket.Arn}/${MediaUploadPrefix}*`), and the specific DynamoDB tables
  plus GSI. No wildcard admin.

- **Scoped `bedrock:InvokeModel`.** The worker role grants
  `bedrock:InvokeModel` / `bedrock:InvokeModelWithResponseStream` scoped to the
  single configured foundation-model ARN (`${BedrockModelId}`) only.

- **No embedded secrets.** The template embeds no secrets; the `BedrockModelId`
  is plain configuration, not a secret, and the Lambda code is a deployable
  inline placeholder.

- **Retain policies for data safety.** All stateful resources (the S3 bucket,
  both DynamoDB tables, and the log groups) use `DeletionPolicy: Retain` and
  `UpdateReplacePolicy: Retain`, so a stack delete never silently destroys data.
  Teardown is a deliberate two-step (empty the bucket, then delete the stack).

> Note: the stack is **authored, not deployed** in this environment (see
> `docs/limitations.md`). These are the template's declared properties, verified
> by `test_template.py`, not a claim of a live deployment.
